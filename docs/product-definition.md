# Product Definition: Annual Review

## 一句话定位

Annual Review 是 Obsidian 的年度复盘工作流插件，帮助用户从一年的笔记中
筛选重要主题、复核关键笔记、形成行动决定，并输出可追溯、可编辑、
可重复生成的 Markdown 年报。

## 定位转换

旧定位容易被理解为“年度统计报告生成器”：扫描 vault、聚合指标、生成图表和总结。

新定位是“可信、有选择、有行动结果的年度复盘工作流”：

- 统计只负责发现线索。
- 候选只负责降低回看成本。
- Review Board 负责让用户做判断。
- 行动决定负责把复盘变成下一步。
- Markdown 年报负责沉淀结果和证据。

## 第一性原理

1. 复盘流程优先：年报是最终工件，核心体验是引导用户完成筛选、确认、取舍和行动。
2. 证据优先：每个主题、笔记推荐和行动建议都应能回到源笔记、标签、链接、任务或时间线。
3. 用户判断优先：插件只给候选项、理由和证据；最终主题、价值判断和行动决定由用户确认。
4. 小闭环优先：先跑通扫描、候选、审核、决策、年报，再扩展图表、导出和分享。
5. 本地与可回滚优先：默认无网络；不覆盖用户编辑；生成内容可备份、可 diff、可复核。

## 核心用户痛点

用户一年写了很多 Obsidian 笔记，但年底面临四个问题：

- 不知道哪些内容值得回看。
- 不知道哪些主题真正贯穿全年。
- 不知道哪些笔记应继续推进、合并、归档或放弃。
- 不信任自动生成的漂亮总结。

Annual Review 的回答不是“替你总结”，而是“帮你把值得判断的东西摆出来，并保留为什么”。

## 产品闭环

```text
选择年份和范围
  -> 扫描 vault
  -> 生成候选
  -> Review Board 审核
  -> 行动决策
  -> Markdown 年报
```

用户完成一次复盘后，应获得：

- 至少 3 个已确认年度主题。
- 至少 5 篇已确认代表笔记。
- 至少 3 条行动决定。
- 每个结论背后的 evidence links。
- 一份可继续编辑、可重新生成、可 diff 的年度 Markdown 报告。

## 核心对象

| 对象 | 定义 | 用户价值 |
| --- | --- | --- |
| Note Signal | 从 Markdown、属性、标签、链接、任务和时间线提取的本地信号 | 让候选不是凭空生成 |
| Candidate | 插件提出的主题、笔记、项目、行动或沉睡资产候选 | 降低回看和筛选成本 |
| Evidence | 源笔记、标签、链接、任务、摘录或时间线 | 让用户能复核推荐理由 |
| Review Decision | 用户确认的继续、合并、归档、放弃或转项目决定 | 把复盘变成行动结果 |
| Annual Report | 保存在 vault 内的 Markdown 年报 | 让结果可编辑、可版本管理、可重复生成 |

## 信任边界

插件可以：

- 扫描当前 vault 内允许范围的 Markdown。
- 生成候选项、理由和证据链接。
- 帮用户组织 Review Board。
- 把已确认内容写入 Markdown 年报。
- 在用户显式同意时，用 AI 辅助润色已确认内容。

插件不应该：

- 默认访问网络。
- 默认调用外部 AI。
- 把自动判断伪装成用户结论。
- 覆盖用户手写年报内容。
- 读取 vault 外部文件。
- 把图表或 provider 数量放在复盘闭环之前。

## 产品语气

应该强调：

- 本地优先。
- 证据链接。
- 用户确认。
- 可回滚。
- 可编辑 Markdown。
- 小闭环复盘。

应该避免：

- “一键生成完美年报”。
- “AI 自动替你理解全年”。
- 过早强调 agent 安装。
- 过度承诺 provider 生态。
- 泛泛描述图表、分享和导出扩展。

## 成功标准

- README 首屏 10 秒内能说明插件解决什么痛点。
- 用户 10-15 分钟内能完成第一轮有意义的年度复盘。
- 每个推荐项都有“为什么被选中”的简短理由和证据链接。
- 重新生成不会抹掉用户手写内容。
- 默认模式无网络请求。
- 年报能清楚区分插件生成内容和用户判断内容。
