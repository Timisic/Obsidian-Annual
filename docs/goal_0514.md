# Run Prompt-vs-Plugin benchmark and optimize report insight quality

Label: `ready-for-agent`  
Type: AFK long-running benchmark + implementation issue  
Blocked by: None — can start immediately

## Context

We need to prove whether **Obsidian Time Range Review** creates product value beyond a strong pure-prompt baseline.

The comparison is not "can the plugin write prettier prose?" The comparison is whether the plugin helps a user rediscover notes, notice hidden cross-note relationships, verify evidence, preserve review decisions, and receive a final **Narrative Review Report** that feels useful to reread.

## Goal

Run a fair benchmark between:

1. **Pure prompt arm** — a strong model receives the benchmark prompt and the same allowed source notes.
2. **Plugin arm** — the plugin uses the same vault snapshot and date range, then follows the product loop: scan, compile evidence, generate Theme Hypotheses, review candidates, make Theme Decisions, and generate a Review Report.
3. **Independent review arm** — a separate reviewer agent evaluates both outputs and decides whether the plugin is meaningfully better, equivalent, or worse.

If the reviewer finds that the plugin is not clearly better than the pure-prompt baseline, optimize the plugin and rerun the loop. After every plugin optimization that produces a new Review Report, run the independent review again before making another optimization.

The final deliverable is an honest benchmark + optimization report. It should say whether the plugin currently has a real advantage, what changed, and what still fails.

## Product hypothesis under test

The plugin should win because it creates a trusted review workflow, not because it has a nicer prompt.

The plugin should help users:

- catch important notes they would otherwise miss;
- connect clues across folders, dates, links, and recurring concepts;
- see why Theme Hypotheses were proposed before they become conclusions;
- review, rename, merge, ignore, and preserve Theme Decisions;
- jump back to exact Evidence Notes in Obsidian;
- generate a readable, low-template **Narrative Review Report** from confirmed themes;
- preserve user-authored report content on regeneration;
- know what evidence scope was scanned or sent to AI.

If the plugin only matches the pure prompt on prose quality, mark that as a product-direction warning, not a victory.

## Agent roles and isolation protocol

Use separate Codex native subagents or clearly separated passes when useful.

### 1. Direct Prompt Agent

Purpose: produce the strongest fair pure-prompt baseline.

Rules:

- Read `docs/prompt-vs-plugin-benchmark.md`.
- Use the benchmark prompt unchanged except placeholders.
- Read the allowed fixture notes as input.
- Do not inspect plugin internals or implementation code for advantage.
- Output theme hypotheses, representative evidence, hidden/old notes, uncertainties, manual review targets, report draft, and evidence table.

### 2. Plugin Run / Implementation Agent

Purpose: run the plugin path and, if needed, improve plugin behavior.

Rules:

- Use the same vault snapshot and date range.
- Follow the intended product loop, not a shortcut that only calls the final report renderer.
- Review at least the top 5 Theme Hypotheses as if acting for an AFK benchmark: accept strong candidates, rename awkward titles, merge duplicates, ignore unsupported weak themes.
- Preserve the distinction between **Theme Hypothesis** and confirmed report theme.
- Save Review Board / state artifacts needed to understand the decisions.
- If optimizing, make small, generalizable changes. Do not hardcode fixture-specific note titles, phrases, dates, or expected winning themes.

### 3. Independent Reviewer Agent

Purpose: judge both outputs and decide whether plugin value is real.

Rules:

- Review both outputs against the source notes and canonical docs.
- Prefer blind review first: call outputs `A` and `B` before revealing which arm produced which report.
- Evaluate both the final report and the evidence/review artifacts.
- Do not accept plugin claims without checking citations and representative evidence.
- After blind scoring, unblind and write the final verdict.
- If the plugin is not better, identify the exact failure modes that should drive the next optimization.

The independent reviewer is mandatory after every plugin optimization iteration that produces a new Review Report.

## Review rubric

Use a 0-5 score for each category, plus concrete evidence comments.

| Category                | What to judge                                                                                                                                 |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Missed-note recovery    | Did the output surface important older, hidden, or low-obviousness Evidence Notes?                                                            |
| Cross-note insight      | Did it connect notes across time, folders, links, repeated concepts, or contradictions in a way a human might have missed?                    |
| Evidence grounding      | Are claims supported by exact Evidence Notes? Are citations faithful rather than decorative?                                                  |
| Uncertainty handling    | Does it separate observed facts from inference and show weak/contradictory evidence?                                                          |
| Reviewability           | Can a user inspect, accept, rename, merge, ignore, or verify the claims without rewriting prompts?                                            |
| Obsidian usefulness     | Are note links exact, readable, and useful for jumping back into the vault?                                                                   |
| Report readability      | Does the Review Report read like a thoughtful human-facing narrative rather than a field template or audit export?                            |
| Insight density         | Does the report contain specific, surprising, or personally useful observations rather than generic productivity/self-growth prose?           |
| Doc alignment           | Does it obey confirmed-themes-only, narrative-not-audit-export, Representative Evidence, Activity Evidence, and User Reflection requirements? |
| Reproducibility/privacy | Are scope, provider/model, prompt, evidence package, state, and report artifacts auditable?                                                   |

### Human cognition / low-template criteria

The final report should feel like a person carefully read the notes and is helping the user notice what they might have missed.

It should:

- lead with concrete tensions, changes, and patterns rather than generic summaries;
- name the actual evidence trail behind an insight;
- explain why two notes belong together, not merely list them together;
- preserve meaningful source-note wording when it carries signal;
- include worth-rereading notes because they matter, not because the template needs a section;
- ask reflective questions that arise from the evidence, not generic coaching questions;
- avoid repetitive section scaffolding, field labels, and mechanical phrases;
- avoid unsupported psychological conclusions about the user.

## Passing threshold

The plugin passes only if the independent reviewer can defend a clear advantage over the pure prompt baseline.

A pass requires all of the following:

- Plugin score is higher overall, not merely tied.
- Plugin is at least as good as the direct prompt on important theme discovery.
- Plugin is better on at least two workflow-differentiating categories, such as missed-note recovery, evidence grounding, reviewability, Obsidian usefulness, decision persistence, or reproducibility/privacy.
- Plugin final **Narrative Review Report** is not materially worse than the pure prompt report on human readability and insight density.
- The verdict does not rely on subjective prose taste alone.

Mark as fail or inconclusive if:

- the pure prompt finds the same or better themes and evidence with similar effort;
- the plugin report has obvious template smell, audit-export residue, or generic filler;
- plugin citations are unsupported, broken, or less useful than the prompt baseline;
- the plugin cannot show why themes were proposed before final prose generation;
- Theme Decisions are not preserved or are not visible in artifacts;
- final conclusions depend on cherry-picked runs.

## Optimization loop

Run this loop until the pass threshold is met, the time budget is exhausted, or there is no safe meaningful improvement left.

### Iteration 0 — Baseline

- Freeze the vault snapshot.
- Run the direct-prompt arm.
- Run the plugin arm.
- Run independent blind review.
- Write the first verdict.

### Iteration N — Diagnose and optimize plugin

If the plugin does not clearly win:

1. Identify the top 1-3 failure modes from the reviewer verdict.
2. Map each failure to the smallest generalizable product/code change.
3. Add or update regression tests before behavior changes when possible.
4. Implement the smallest useful change.
5. Run focused tests.
6. Generate a new plugin Review Report.
7. Run independent review again.
8. Archive the diff summary, test evidence, and reviewer verdict in the iteration folder.

Possible optimization areas:

- **Evidence Package selection**: improve coverage of long-tail notes, older resurfaced notes, cross-folder clusters, and non-obvious relationships.
- **Theme Hypothesis generation prompt**: require more concrete connection reasoning, contradictions, and manual review targets.
- **Review Candidate identity/state**: preserve decisions across reruns and make drift visible.
- **Representative Evidence selection**: choose fewer, stronger, more explanatory links rather than dumping evidence.
- **Report renderer**: reduce template smell, absorb connection explanation into prose, improve aliases, remove audit residue.
- **Reflection questions**: make questions evidence-born and uncomfortable/concrete, not generic action items.
- **Worth Rereading**: prioritize notes that actually unlock an insight or hidden connection.
- **Benchmark harness**: improve reproducibility and artifact capture without changing product behavior.

Do not optimize by weakening the prompt baseline, hiding failed plugin runs, hardcoding fixture-specific answers, or adding new dependencies.

## Non-goals

Do **not** do these in this issue:

- Do not create a new product pivot without benchmark evidence.
- Do not add new AI providers.
- Do not add new dependencies.
- Do not redesign the entire Review Board UI unless a narrow change is required for reviewability.
- Do not build a full Evidence Audit export unless needed as a minimal artifact for this benchmark.
- Do not remove Activity Evidence charts from the Review Report.
- Do not write unreviewed Theme Hypotheses into the Review Report.
- Do not make sensitive-detail redaction the default behavior.
- Do not edit source fixture notes to make the plugin look better.

## Required implementation discipline

- Check `git status` before editing.
- Do not revert unrelated user changes.
- Keep diffs small and reversible.
- Prefer deletion or prompt/report simplification over adding new abstraction layers.
- No new dependencies unless a human explicitly approves.
- Every behavior change needs focused tests where practical.
- Keep benchmark artifacts separate from production fixture source files.
- Commit after meaningful green phases if running in a commit-capable workflow, using the repo Lore Commit Protocol.

Write a final benchmark report in the run folder and summarize it in the issue/PR output.

```md

## Executive verdict

Pass / Fail / Inconclusive, with one paragraph explaining why.

## What the pure prompt did better

Concrete findings, not defensiveness.

## What the plugin did better

Concrete findings tied to Evidence Notes, Review Board state, navigation, or reproducibility.

Honest gaps, especially if plugin value is still weak.

## Next recommended issues

Only include follow-ups that are grounded in benchmark evidence.
```

The final user-facing summary should include:

- changed files;
- benchmark artifacts path;
- direct-prompt vs plugin verdict;
- independent reviewer conclusion;
- tests run and results;
- remaining risks.

## Stop condition

Stop only when one of these is true:

- the plugin has passed the threshold with independent reviewer evidence;
- the overnight/time budget is exhausted and the final report honestly states current fail/inconclusive status;
- a hard blocker prevents running the benchmark or tests, and the blocker plus next recovery step are documented.

Do not stop after implementation alone. The issue is complete only after the independent review and final benchmark report exist.
