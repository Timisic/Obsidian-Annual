````md
## Context

The current generated Review Report is too close to a Review Board / audit export. It contains field-style AI sections, full evidence lists, local signals, merge sources, hidden connections, and technical methodology details that make the report noisy and hard to reread.

## Goal

Implement the default **Narrative Review Report** shape across Annual, Quarterly, Monthly, and Custom Range Review Sessions.

The report should be a readable, theme-first Markdown review artifact, not a field-by-field audit export.

A successful report should feel like:

1. A concise overview of the time range.
2. A compact activity rhythm section that preserves charts.
3. A small number of strong prose-led themes.
4. Representative evidence links with readable aliases.
5. Worth-rereading notes.
6. Reflection questions.
7. A protected user-written section.
8. A very short methodology note.

## Required report shape

Default generated reports should follow this conceptual structure:

```md
# <range label>

## 总览 / Overview

2-4 prose paragraphs explaining the main change, tension, and meaning of the time range.

## 年度节奏 / 阶段节奏 / Activity Rhythm

Keep the existing chart embeds.

Each chart gets a short human-readable interpretation.

## 主要主线 / Main Themes

### Plain Markdown theme title, not a wikilink

Prose-led narrative. No field-style labels.

Representative evidence:

- [[exact/path/to/source|Readable alias]]: short explanation.
- [[exact/path/to/source|Readable alias]]: short explanation.

Optional uncertainty sentence if useful.

## 值得重读的笔记 / Worth Rereading

A short list of notes worth rereading and why.

## 留给自己的问题 / Reflection Questions

Questions, not action items.

## 我的补充 / User Reflection

Protected user-written section. Regeneration must preserve it.

## 方法与数据口径 / Methodology

Very short human-readable note only.
```
````

Exact Chinese/English headings may follow existing localization patterns, but the structure and meaning must match the documented target.

## Theme rendering requirements

- Theme titles must be plain Markdown headings, not wikilinks.
- Use only user-confirmed themes:
  - accepted / renamed themes enter the report.
  - ignored themes do not enter.
  - merged source themes do not appear independently.
- Use the user-renamed title when present.
- Do not render these field labels in the default report:
  - `AI 总结`
  - `为什么这个主题存在`
  - `连接解释`
  - `本地信号`
  - `复核提示`
  - `合并来源`
  - full `证据笔记` audit lists
- Absorb connection explanation into theme prose.
- Each theme should cite only 2-4 **Representative Evidence** links.
- Evidence wikilinks in the report body must use readable aliases.
- Link targets must remain exact vault-relative note paths.
- Aliases may be generated for readability, but must stay faithful to the source note and must not become unsupported conclusions.
- Default output may preserve names, relationship details, and money details from source evidence. Do not redact by default.

## Theme count requirements

- Annual and Quarterly reports should normally target 3-5 strong themes.
- Monthly and Custom Range reports may also use 3-5 when evidence supports it.
- Short or sparse ranges may have fewer than 3 themes.
- Do not force weak signals into themes just to hit a number.
- Weak but interesting notes should move to Worth Rereading rather than become fake themes.

## Activity Evidence requirements

- Preserve existing chart assets and embeds, including cumulative growth, growth trend, heatmap, and topic evolution where currently supported.
- Charts belong in a compact Activity Rhythm section.
- Do not turn charts into the main product identity.
- Avoid large metrics tables in the main reading flow unless tests/docs explicitly require them.
- Each chart should have a concise human-readable interpretation.

## Worth Rereading requirements

Replace the current machine-task feel of `重新发现的笔记`.

- Use a reader-facing concept like `值得重读的笔记`.
- Do not say things like “补 2-3 个上下文链接后整理成输出草稿”.
- Each item should explain why the note is worth rereading.
- Links must use readable aliases.

## Reflection Questions requirements

Replace task-like review prompts with questions.

- Use questions, not action items.
- Do not write “下一步行动”, “整理成项目”, or automatic to-dos.
- Questions should connect back to confirmed themes where possible.

## Methodology requirements

Keep methodology very short.

It may explain:

- time range
- evidence source
- AI usage boundary
- confirmed themes require user review

It must not list detailed technical口径 in the default report, such as:

- full include/exclude directory lists
- snapshot implementation details
- language setting
- frontmatter count details
- filesystem fallback counts
- raw local signal fields

Detailed audit material belongs in Review Board state or a future explicit Evidence Audit export.

## User Reflection requirements

- Keep a visible human heading such as `## 我的补充`.
- Keep machine markers only as protection mechanics.
- Regeneration must preserve user-authored content.
- Existing report writer behavior around generated/user block merging must remain safe.

## AI prompt / provider requirements

If AI-generated prose is used:

- Update prompts so the model is asked for prose-led narrative, not field-style reports.
- Remove or narrow any instruction that conflicts with readable aliases in reports, such as preserving paths without aliases.
- Still require exact evidence paths/ids for traceability.
- AI may organize confirmed themes into readable prose, but cannot change theme identity, user decisions, or evidence boundaries.
